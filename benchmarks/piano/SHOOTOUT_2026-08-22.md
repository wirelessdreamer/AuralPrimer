# Piano transcription shootout — 2026-08-22

A head-to-head of every piano/keys transcription engine in the tree, focused on
real worship recordings, run against two scoring tiers.

Runner: `run_piano_shootout.py` · Report: `report_piano_shootout.py` ·
Sheet alignment: `align_sheet_reference.py` · Manifest: `piano_shootout_2026-08-22.json`

## Material

**Real songs** (tier `song`) — htdemucs_6s `piano.wav` stems, full length:

| Song | Source | Length |
|---|---|---|
| Center | Bethel Music, Abbie Gamboa (Live) | 7:46 |
| What A God | SEU Worship | 7:14 |
| King of My Heart | Steffany Gretzinger / Jeremy Riddle / Christine Rhee (w spontaneous) | 17:26 |
| King of My Heart (edit) | same take, cropped to one pass through the chart form | 6:05 |

**Gold tier** (tier `gold`) — 10 Piano Psalms keyboard stems with paired,
exactly-aligned reference MIDI, 34.9 min total. These carry the only
trustworthy absolute accuracy numbers in the run.

## Scoring tiers, and what each is worth

**Gold** — reference MIDI paired with the stem. Real precision / recall / F1 /
velocity MAE / offset accuracy. The reference offset is calibrated per item by
cross-correlating an onset-strength envelope against the reference onset train
(`calibrate_offset`), so no transcription engine influences the alignment every
engine is then scored against. Validated against four cases whose offsets were
hand-calibrated in the previous manifest: recovered to within 36 ms (three of
four within 11 ms). This matters — real offsets reach −0.475 s, so an
uncalibrated gold tier would be meaningless.

**Relative** — the three real recordings. No note-level ground truth, so
engines are scored against a cross-engine consensus (notes at least a third of
the producing engines agree on). This measures *agreement*, not correctness: an
error most engines share scores as a success. Ranking aid only.

**Sheet-derived** — available once official sheet music is supplied; see below.

## Getting sheet music in

Official piano/vocal arrangements exist for all three songs (PraiseCharts,
SongSelect) but are paid downloads that must be fetched by the account holder.
**Prefer MusicXML or MIDI over PDF** — the sidecar already parses MusicXML
(`aural_ingest.musicxml_import`) and MIDI directly, whereas a PDF would need an
OMR pass (no Audiveris, MuseScore or JRE on this machine).

```bash
python benchmarks/piano/align_sheet_reference.py --run <run_dir> --item center --sheet "path/to/Center.musicxml"
```

That writes `<run>/references/<item>.json`; re-running `report_piano_shootout.py`
then scores the **already-cached** predictions against it. No transcription is
re-run.

### What sheet alignment is worth

Alignment uses **synctoolbox** (International Audio Laboratories Erlangen):
multi-resolution MrMsDTW with DLNCO onset features, which is built for exactly
this problem — synchronising long recordings where chroma alone lacks attack
precision. Install it before aligning (benchmark-only, deliberately not in
`requirements-dev.txt`, which is kept light):

```bash
python -m pip install synctoolbox
```

Three design choices, each measured on a synthetic case (a Psalm's own
reference MIDI re-tempoed 6% and transposed down a fifth, re-aligned to its
audio, then compared against the known answer):

| Method | median | p90 | within 60 ms |
|---|---|---|---|
| Sonify the score, then MrMsDTW | 1908 ms | — | 4% |
| Plain chroma-DTW (fallback, `--method chroma`) | 55 ms | 740 ms | 55% |
| MrMsDTW on score features | 54 ms | 87 ms | 64% |
| **MrMsDTW + self-calibrated lag (default)** | **13 ms** | **41 ms** | **95%** |

- **Score features are built directly, not sonified.** The score already *is* a
  pitch activation matrix; synthesising audio and re-estimating pitch from it
  throws away exactness and cost two orders of magnitude of accuracy.
- **The transposition shift goes on the audio side.** `compute_optimal_chroma_shift(X, Y)`
  returns the shift to apply to *Y*; applying it to *X* inverts the correction and
  the path wanders by seconds (median 4.8 s) while still reporting the right key.
- **A constant residual lag is removed.** The pitch-feature window trails the true
  attack by ~50 ms. It is measured against the audio's own onset envelope — no
  ground truth involved — and subtracted. This alone takes 64% → 95%.

Transposition is recovered exactly, so the published key need not match the
recording. At 95% of reference notes inside the scoring tolerance, a
sheet-derived reference is now good enough to read as near-accuracy rather than
merely a ranking aid — with one caveat that no alignment can fix:

- Published arrangements are simplified. Genuine embellishment by the player
  still scores as a false positive, so the report separates score-covered from
  score-absent regions.

### King of My Heart needed an edit

The full take is 17:26 and runs the form several times before leaving it, so no
single monotonic pass through a ~4-minute chart can cover it. Chroma
self-similarity cannot segment the song either — every section matches every
other above 0.98, because the whole song is one 4-chord vamp.

The cut is taken from the arrangement instead. At **06:04** the drums drop from
−29 to −86 dBFS and the guitar from −28 to −80 in two seconds while the piano
takes over; 10:15–11:45 is a near-total band dropout. So
`king_of_my_heart_edit` is **00:00–06:05.36** (a beat boundary just after the
band's final hit) with a 1.2 s fade, giving one clean pass through the chart
form. The uncropped take stays in the manifest as its own item, so the
spontaneous section is still measured — just not against a chart.

## Engine roster

24 engines. `piano_pti*` are **force-enabled** via `AURAL_ENABLE_PIANO_PTI=1`:
`transcription.piano_pti_enabled()` disables all six under torch ≥ 2, citing NaN
velocities and ~100× note explosion, but on torch 2.11 + RTX 5090 they produce
plausible output (210 sane notes on a 10 s excerpt; thousands over a full song).
Whether that gate is now stale is one of this round's questions — the metrics
decide it.

Excluded, with reasons rather than silent zeros:
- `piano_hft` — no local checkpoint; needs `AURAL_PIANO_HFT_CHECKPOINT` plus an
  external command. Weights are license-gated.
- `piano_d3rm` — checkpoints are on disk (`assets/models/piano_d3rm/D3RM.ckpt`)
  and the repo is at `D:/Code/d3rm`, but it ships only a PyTorch-Lightning
  MAESTRO-test-set harness, not an arbitrary-audio CLI.

`melodic_rmvpe` returns zero notes on every item in ~0.1 s — the same
silent-zero shape as the PTI gate, and worth its own verdict.

## Running it

```bash
python benchmarks/piano/run_piano_shootout.py run --manifest benchmarks/piano/piano_shootout_2026-08-22.json --workers 12 --gpu-workers 3
```

Tasks are one subprocess per (item, engine) with a timeout, so a hang, crash or
CUDA OOM in one engine cannot take down the run. Predictions are cached per
(item, engine), and `--resume` (default) skips anything already on disk, so the
run is interruptible and restartable.

## Gotcha worth knowing

demucs 4.0.1's Python API writes **float32 WAV**, and the shared
`read_wav_mono_normalized` reader uses the stdlib `wave` module, which rejects
format 3 and — because the exception is swallowed — returns an empty list. Every
DSP engine then reports zero notes rather than an error. `piano_polyphonic` went
from 0 to 16,039 notes on the same stem purely by converting it to PCM_16. All
stems in this run are PCM_16, which also matches the gold-tier fixtures so audio
format is not a confound between tiers.

Separately, `demucs.separate` itself now fails on torch 2.11 with
`ImportError: TorchCodec is required for save_with_torchcodec`; separation here
goes through `apply_model` and writes via soundfile instead.
